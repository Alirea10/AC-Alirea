# ArkChess 赛季开发协作

## 项目目的与仓库边界

ArkChess 是基于《明日方舟》的自走棋赛季开发项目。赛季玩法由多仓共同实现：

| 仓库 | 作用 | 处理需求时优先检查 |
|---|---|---|
| D:/Dev/arkchess/ArkChess | 当前赛季数据、JSON 字典、Buff 模板、图标和设计稿 | 当前工作树、project.json、相关字典和模板 |
| D:/Dev/autochess-season-editor | 人类可视化设计和编辑赛季数据 | packages/shared 类型与规范化、packages/editor 页面、导入保存导出 |
| D:/Dev/autochess-server | 赛季解析、协议、房间和部分运行规则 | 赛季解析器、规则运行时、赛季响应和持久化 |
| D:/Dev/autochess-v077-port | 新版 PC 与 PE 共用客户端和原生游戏适配 | 赛季转换、Buff/事件链、原生注册、资源与双端入口 |
| D:/Dev/autochess-client | 旧版客户端及历史实现参考 | 仅在确认旧版适用或追溯差异时检查 |
| D:/Dev/ArknightsAssets-Gamedata-git | 明日方舟原版内容解包 | cn/gamedata/ 中原版配置、模板、角色和战斗资源 |

目录、分支和合并目标以 D:/Dev/autochess-v077-port/docs/ai/project-guide.md 为准。仓库内 AGENTS.md 是本地入口；本 skill 只补充 ArkChess 专属约定。

## 事实来源与跨聊天接续

1. 用户本轮明确要求优先，其次检查当前工作树与目标分支；历史聊天、记忆、旧设计稿和提交记录只用于定位。
2. 当前赛季实现以 ArkChess 当前数据和对应 server/editor/client 代码为准。工作树有未提交差异时，区分 HEAD 与当前文件内容，避免把其中一个误称为另一个。
3. ArknightsAssets-Gamedata-git 是原版游戏内容的权威参考。仅用它确认原版已有角色、技能、Buff、事件和资源，不用它替代自定义赛季运行链检查。读取前确认目录存在并记录数据版本或 Git 提交。
4. 设计稿描述当前实现时，必须回到数据字段和代码；不能因旧稿写了某效果便认定它仍然存在。
5. 静态数据、结构校验、编辑器构建、赛季安装回读、页面验收和实际对局是不同证据等级。说明结论时逐项写清已验证范围。

开始前在受影响仓库检查分支、git status --short、暂存区和工作树列表。保留已有用户改动与已有暂存内容；仅操作本轮明确涉及的文件和差异块。

## 从设计到实际运行的追踪

先确定当前活动赛季目录，再沿以下数据链逐项核对：

1. 棋子：charShopChessDatas/ 的商店记录 → charChessDataDict/ 的战斗记录、升阶关系和特质绑定 → bondInfoDict/ 的盟约成员及盟约层数 → project.json、模式名单和查找表中的注册。
2. 盟约：bondInfoDict/{bondId}.json 的成员、激活条件、盟约描述和描述参数 → effectInfoDataDict/ 的局内展示文本 → effectBuffInfoDataDict/ 的效果注册及 Blackboard → buffTemplates/ 的事件、条件、目标选择、Buff 创建和实际数值节点。
3. 特质：棋子上的 garrisonIds → garrisonDataDict/garrison_编号_阶位.json 的事件、类型、描述与 Blackboard → 对应 Buff 模板、服务端事件或客户端事件处理。
4. 导入与导出：编辑器 shared 类型和规范化 → 单 JSON / 目录读写 → server 解析和下发 → PC / PE 导出筛选 → 客户端安装、资源登记和原生表写入。

不要从一个 Buff 名称或展示文本直接跳到“已实现”。需要继续检查触发事件、事件过滤、父子 Buff、作用目标、属性类型和实际执行节点；如果原生引擎调度仍不清楚，标为静态链路证据并保留运行验证问题。

## ArkChess 数据命名和结构

- 普通与精锐战斗棋子通常分别为 _a、_b。新增自定义棋子按 chess_主盟约缩写_阶级_本阶序号_a/b 命名；阶级和序号从当前代码中同类记录核对，不猜空缺编号。
- 特质文件按 garrison_序号_a/b 命名；确有不同阶位或效果时才使用 _c。普通、精锐文件及棋子绑定必须成对核对。
- 效果、Buff 模板和其他 ID 前缀并不统一。先从该盟约或特质现有 effectId、效果记录、模板引用和项目注册追踪，禁止用名字推导文件前缀。
- 新增盟约需同步成员列表、普通/精锐棋子关系、商店可见记录、效果记录、模板引用、模式名单和盟约分类；只补其中一个 JSON 文件不构成完整链条。
- buffTemplates/ 中已有模板按只增不删维护：保留旧键、键顺序及用户内容，只添加本次确实需要的字段或节点。编辑器固定模板是编辑能力，活动赛季自己的模板才是本次运行数据。
- 有运行聚合数据时，要确认它是源码、生成物还是忽略文件；分模板与聚合使用情况分别核对。不要只改分文件后便宣称游戏运行时会读取它。

## 盟约富文本与成长描述

盟约相关描述通常有两个显示位置，必须分别核对并保持含义一致：

- bondInfoDict/{bondId}.json 的 desc：盟约资料中的说明。
- effectInfoDataDict/{effectId}.json 的 effectDesc：局内盟约效果说明。

统一采用游戏富文本标记，不把标记当作 HTML 改写：

| 标记 | 用途 |
|---|---|
| &lt;@ba.vup&gt;文字&lt;/&gt; | 蓝色增益文字 |
| &lt;@ba.vdown&gt;文字&lt;/&gt; | 红色负面文字 |
| &lt;@autochess.dgreen&gt;文字&lt;/&gt; | 绿色的中性标示文字，常用于人数、条件和范围 |
| &lt;@ba.acrem&gt;文字&lt;/&gt;、&lt;@autochess.gray&gt;文字&lt;/&gt; | 淡化注释 |

闭合标记写作 &lt;/&gt;。修改后检查每段标记配对、换行、条件人数及语义；不要把中性条件误标为增益或减益。

成长数值占位符使用 {索引:格式}。索引按 descParamBaseList 和 descParamPerStackList 中相同下标配对，键值来自该盟约效果的 Blackboard；格式带 % 时按百分比显示，不带 % 时显示普通数值。默认描述计算为“基础值 + 每层增量 × 盟约层数”。如果每若干层才增加一次，按统一项目指南的 bond-description-steps.md 设置 {每层参数键}.stack_step，计算使用向下取整。战斗 Buff 必须使用相同的分档参数，描述显示本身不能改变实际 Buff。

卫戍协议中凡是需要随盟约层数成长并在局内展示的数值，都填写对应的基础参数列表和每层参数列表；数组长度、下标、Blackboard 键、百分比格式与效果节点相互核对。固定值无需伪造增长参数。

## 赛季编辑器约束

- 先检查编辑器现有类型、页面、导入/保存/导出、校验和数据流是否能承载需求。编辑器能完成的部分只改编辑器与赛季数据，不改客户端或服务端。确需修改客户端或服务端时，先用代码或数据流证据确认编辑器缺少所需能力，向用户说明缺口及拟修改仓库和范围，取得明确许可后再改；许可前继续不依赖该修改的工作。
- 编辑器是人类可视化编辑工具；它不是赛季语义的唯一实现端。改数据结构前，检查 packages/shared 类型、目录拆分/合并、编辑页面、保存、普通 JSON 导出、PE 导出及 server 解析。
- 目录模式会将不同字典拆分保存，project.json.constFields 保存另一部分常量。新增字段时确认真实归属，并比较目录读写与 JSON 导入导出结果。
- UI 展示类型与 JSON/wire 类型分开处理。协议或赛季契约声明 string[] 时，数字输入框可以显示数字，但保存和导出仍需保持字符串。使用自定义记录核对，不能只看内置记录。
- 模板采用增量编辑，保持既有数据和字段顺序。导入文件按用户选择的文件名直接导入；目录批量读取采用一个 Worker 和有界的同赛季并发读取。
- PE JSON 使用单独兼容导出入口。新增数据或新主盟约时，检查 PE 过滤规则和所有被过滤字段的引用，确认 PC/PE 的适用性。
- 可视化页面改动按用户要求验证保存、刷新恢复、选择和导出；不要把 TypeScript 构建成功等同于页面验收或对局验收。

## 设计稿与 README

docx/设计稿/ 中每个主盟约一份独立 Markdown。统一采用以下结构：

1. 标题、状态和回写日期。
2. 当前实现概览：盟约 ID、激活门槛、成员数与数据口径。
3. 干员表：角色名、阶级、棋子数据 ID、其他盟约和特质 ID。
4. 两个富文本显示位置的现行内容。
5. 实际 Blackboard 数值、Buff 模板和关键特质链。
6. 源码中的差异、疑点与尚未验证的事项。

已实现盟约从当前代码反写，不把“原设计”混进现行效果。未实现的雷姆必拓文档只保留为设计阶段资料，明确标注未回写，不把工作树里尚未确认的部分实现升级成已完成结论。若 README 中盟约汇总与代码冲突，说明差异并核验来源。

当核心盟约列表出现新盟约时，在根目录 README.md 的盟约体系中新增一行，先写代码可证实的中文名、ID、普通/精锐记录数、激活门槛和一句当前效果摘要；不替用户扩写设计背景或主内容。README 现有未提交改动与描述由用户撰写的部分要原样保留。

- 按用户本轮范围验证。测试代码、夹具和临时数据放系统临时目录，不加入暂存区或提交。

- 提交前检查钩子和 core.hooksPath。采用明确文件范围；完整检查暂存 diff。一个文件混有本次和旧改动时，仅暂存本次差异块。
- 提交标题使用中文类型，例如 docs: 统一盟约设计稿和项目 AI 指南，正文留空行并列出改动。遵循统一项目指南的本地合入、工作树检查与清理规则；不推送远端，除非本轮明确要求。
- 交付摘要说明变更文件、关键规则、实际验证和未验证范围。不要把静态检查描述成对局或线上验收。
